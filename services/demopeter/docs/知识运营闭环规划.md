# DemoPeter 知识运营闭环规划

> **版本基线：** 包含 D-Indexer 断点续传  
> **目标读者：** 项目团队（产品、后端、全栈、Agent/集成）  
> **最后更新：** 2026-06-09

---

## 1. 背景与现状

DemoPeter（szpeter2026 知识库平台）已完成第一阶段 RAG 能力，并新增 D 盘代码索引模块：

| 能力 | 状态 | 说明 |
|------|------|------|
| 检索 + AI 问答 | ✅ 已可用 | 混合检索 RRF、DeepSeek/Ollama |
| D 盘代码索引 | ✅ 已可用 | 22 个项目目录自动扫描，支持断点续传 |
| 断点续传扫描 | ✅ 已可用 | 目录级 checkpoint + 文件级缓存 |
| 跨文档缺口推理 | ✅ 刚起步 | RAG 注入文档目录，LLM 推断年份缺口 |
| 缺口可度量、可追踪 | ❌ 未做 | 无覆盖矩阵、无任务池 |
| 内外部自动补料 | ❌ 未做 | Gitea/Outlook 未入库 |
| 人机审核充实闭环 | ❌ 未做 | 无审核队列 |

**核心问题：** 系统会「问、会答、能猜缺口」，但知识库 **不会自己长大**，缺口无法被团队持续运营。

**目标：** 形成可运营闭环：

```
盘点覆盖 → 发现缺口 → 分派/拉取 → 人工审核 → 增量入库 → 复检关闭
         ↑___________________________________________|
```

## 2. 价值主张

| 角色 | 价值 |
|------|------|
| 业务/研究 | 明确知道「缺什么」，不依赖每次向 AI 提问 |
| 运维/数据 | 统一入库、增量同步、操作可审计 |
| Agent/MCP | 自动查覆盖、建任务、触发导入 |
| 外部协同 | Gitea、Outlook 等信息 **进入向量库**，而非只写 Notion |

## 5. 分阶段路线图

### Phase 1 — 可度量的查漏补缺（优先，约 2–3 周）

#### 1a. 结构化覆盖分析（选项 A）

| 项 | 内容 |
|----|------|
| **新建** | `src/coverage_analyzer.py` |
| **规则配置** | 在 `config/corpora.json` 扩展 `coverage_expectations`（按 corpus 定义期望覆盖） |
| **科锐国际示例** | `年份 × {年报, 一季报, 半年报, 三季报}` |
| **API** | `GET /api/coverage/{corpus_id}` |
| **MCP** | `kb_coverage_report(corpus_id?)` |
| **UI** | 报告中心新增「覆盖度」Tab：红/黄/绿矩阵 + 缺口列表 |

**验收标准：**

- 科锐国际：2017 仅 Q3、2020 仅 Q1、2021+ 空白 — 与人工核对一致
- **不依赖 LLM**，结果为确定性规则输出

#### 1b. 统一 import + 增量扫描

> ⚠️ **现状更新 (2026-06-09)**：D-Indexer 已实现断点续传 + 文件级缓存增量扫描。文档管线的增量扫描仍需统一。

| 项 | 内容 |
|----|------|
| **重构** | Web `/api/documents/import` → 调用 `KnowledgeBaseService` |
| **新建** | `scripts/scan_corpus.py` 或 `manage.ps1 scan` |
| **逻辑** | mtime/hash 对比 `documents.file_path`，仅导入变更文件 |
| **可参考** | `d_indexer/checkpoint.py` 的 `indexed_files_cache` 表设计（path + size + mtime 三元匹配） |

**验收标准：**

- CLI（`import_corpus`）、Web、MCP（`kb_import`）三条路径行为一致
- corpus 标签、skip/force 语义统一

#### 1c. 缺口任务池（选项 B）

| 项 | 内容 |
|----|------|
| **Schema** | 新增表 `gap_tasks` |
| **字段** | `id, corpus_id, title, gap_type, status, source, created_at, closed_at, metadata JSON` |
| **任务来源** | 覆盖分析自动创建；RAG 0 命中 / `_below_threshold` 可写入 |
| **API** | `GET /POST /PATCH /api/gaps` |
| **MCP** | `kb_gap_list`、`kb_gap_close` |
| **UI** | 报告中心「待补清单」：待处理 / 进行中 / 已关闭 |

**验收标准：**

- 科锐国际自动生成 ≥3 条缺口任务（如 2017 年报、2020 半年报/年报等）
- 每条任务有唯一 ID 和 status

### Phase 2 — 从使用行为驱动补料（约 1–2 周）

- 挖掘 `query_logs`：0 命中、低相似度、含「缺失/补齐」等关键词
- 自动合并到 `gap_tasks`（去重）
- `report_gen.py` 周报增加「本周未答好 Top N」

### Phase 3 — 内外部自动补料（选项 C，约 2–4 周）

| 连接器 | 改造点 | 建议优先级 |
|--------|--------|------------|
| **Gitea** | push 变更 `.md/.pdf` → `kb_service.import_directory` | 高 |
| **Outlook** | 指定文件夹附件 → `doc_processor` → import | 中 |
| **Notion** | 选定 DB 导出 MD → import | 低 |

**前置依赖：** Phase 1b 统一 import 必须先完成。

---

### Phase 4 — 人机审核充实闭环（约 2–3 周）

```
gap_task → Agent 拉草稿/外链 → Web「待充实」→ 人工确认
         → 写入语料目录 → scan/import → coverage 复检 → close task
```

## 6. 选项 A / B / C 决策建议

| 选项 | 投入 | 依赖 | 建议 |
|------|------|------|------|
| **A 覆盖度矩阵** | 中 | corpora 规则配置 | **必做** — 闭环起点 |
| **B 缺口任务池** | 中 | A 的输出 | **必做** — 让缺口可追踪 |
| **C 自动入库** | 高 | 1b 统一 import | Phase 3，不抢 Phase 1 |

### 推荐 MVP 范围

> **Phase 1 = A + B + 1b（统一 import）**

理由：

1. 科锐国际场景已验证「能推理缺口」，缺的是 **持久化 + 可视化 + 任务化**
2. 不做 1b，Gitea/Outlook 接入会重复 Web/CLI 不一致的问题
3. 没有 A/B，自动入库了也无法确认是否补全
