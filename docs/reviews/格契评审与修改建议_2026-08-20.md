# 格契（GFCC）真源评审与修改建议

> 致：项目组
> 评审对象：`docs/ports/README.md` + `contracts/*.v1.json`（v1.0.0，2026-08-20，szbenyx/gfcc @ gitee）
> 对照基准：《立项报告_AI社区与社区AI》（V1.1）· 产品代号 Tractor 牵引机 · 8 角色 / 4 类营造师 / AI 洞察层 / 双轨对话 / 7 库超级底座
> 日期：2026-08-20 · 版本：v1.0

---

## 一、总评（先看这段）

**这是很好的"契约层"，还差半层"价值层"和一个"判据层"。**

格契把项目方法论成功落成了机器可读契约：八角梯、Dual 七库、CoCo、共识双向确认、六条不变量——工程严谨度 8/10，方法学吸收（Steedar/ethos/Tatha/Agent Runtime）不抄字段，值得保住。

但作为"出发点和落脚点"，对照立项设想逐项核对，**三类关键缺失**：

| 缺失层 | 立项设想 | 格契现状 | 后果 |
|---|---|---|---|
| **人** | 人是目的；4 类营造师是行动枢纽 | 契约里只有 8 级成长梯，无营造师维度；无"为谁而生"的陈述 | "营造"没有执行者；文档读起来像给机器看的，不像给社区看的 |
| **AI** | AI 是共同体成员（洞察层：RAG × 观察评估）；双轨对话（协作 × 教练） | AI 只出现在 `llm` 槽位（provider）和 ethos（verifier）；无观察者身份、无对话模式 | "社区AI × AI社区"的差异化核心没进契约——AI 仍是工具，不是成员 |
| **落脚点** | 记得住 · 协商得了 · 贡献兑得现（成功判据） | 只有工程不变量（invariant），无业务判据 | 无法回答"跑一年，什么算格契真的起作用了" |

一句话判断：**工程真源可以定稿，但建议在 L0 之上加一层"价值层"（L-1），并给每个一等端口补"成功判据"（业务不变量），才配得上"出发点和落脚点"的定位。**

## 三、P0 详解

### 3.1 缺价值层与落脚点判据（最核心的一条）

现状：L0 权威层级写得很好，但整份文档回答的是"**怎么交付**"（契约、端口、不变量），没有回答"**为谁而生、成什么算成**"。

建议：在 L0 之上增加 **L-1 价值层**（不参与机器执行，但约束一切变更），放一句话定位 + 成功判据：

> **定位句（建议直接采用立项定稿）**：AI 时代的社区营造操作系统——人是目的，AI 是基础设施（放大器），社区是对象，营造是动作。
> **品牌呼应**：格契是那份"牵引力"；方向盘在共同体手里（Tractor：你掌方向，我出力气）。

**建议的 5 条成功判据（业务不变量，示例）**：
1. **记得住**：七库中任一记录被后续议题/行动引用（复用率）> 某阈值——记忆不是存进去，是被用起来。
2. **协商得了**：共识 `consensus_verified` 的提案中，证据链（谁评、依据什么）可完整追溯的比例 = 100%。
3. **贡献兑得现**：`contribution.fulfilled` 到 `identity.capability_trace` 的回写闭环比例 > 某阈值。
4. **人往高处走**：有成员完成 observer → participant → proposer 的跨越，且每级都有 Dual/CoCo 证据（不是管理员开关）。
5. **AI 不抢戏**：AI 观察被采纳为共识证据的提案占比 ≤ 某上限（AI 辅助、人决定）。

### 3.2 AI 观察评估缺席

现状：`memory.observe`（min_role: experimenter）、`consensus.score`（system）都只覆盖"人操作"；AI 洞察层（RAG + 观察评估）在契约中无任何挂点。这与立项的最大差异化（"AI 是共同体成员而非工具"）直接冲突——对齐建议书里 G4 指出的问题，在契约层重现了。

建议（三处改动）：
- `memory.v1.json`：`observe` 增加 `observed_by: "human" | "ai"`；AI 观察写入需带 `ai_source`（哪个洞察模型），且**不得**静默改写记忆（遵循 supersede 语义）。
- `consensus.v1.json`：`score` 增加 `evidence` 数组；允许 AI 提供"观察评估"作为评分材料之一，但 `party` 确认必须是人。
- `roles.v1.json`：`transitions.driven_by` 增加 "ai_observed（辅助证据，单独不足以上升）"。

### 3.3 4 类营造师缺席

现状：8 级成长梯是"个人角色成长"，但"营造"的动作需要执行者分工——立项里的 4 类营造师（协作推进 / 赋能项目 / 在地连接 / 持续运营）在契约中无位置。

建议：`identity.v1.json` profile 增加：

```json
"builder_tags": {
  "type": "array",
  "items": { "enum": ["collaboration", "project_enablement", "local_connection", "sustained_operation"] },
  "description": "营造师标签（可多选）。与 roles 成长梯正交：角色=成长阶段，营造师=专业分工。"
}
```

并在一等端口语义中注明：**角色管"能不能"，营造师管"擅长做什么"**。

### 3.4 memory 七库丢"价值"

现状：立项定稿为"议题 / 行动 / 事件 / **方法论价值** / 人 / 组织 / 资源资产"，格契为 `issue/action/event/method/person/org/resource`——"价值"被吞进 `method`。

问题：方法论（how）与价值（why）是两类不同沉淀。社区里"我们为什么这样做"（原则、红线、判断依据）不该和"怎么做的步骤"混在一个库里——格契自己的六条不变量，就应该是 memory 里的一条"价值"记录。

建议（二选一）：
- 方案 A（推荐）：库枚举恢复 `methodology_value`（方法论价值），或
- 方案 B：`method` 库内 `record.type` 增加 `"value"` 子类型，并在 `libraries` 描述中注明"含价值观/原则/红线"。

## 四、P1 详解

### 4.1 共识评分黑盒 → 可解释性

`consensus_passed` 依赖 `score >= 85`，但 85 分怎么来的契约里是空的（`score` 由 system 写）。社区产品的信任基础是"评分可解释"——成员不知道分数依据，"双向确认"就只剩仪式感。

建议：`proposal` 增加 `score_evidence`（数组：`{by_sub, basis, at}`），并允许在 `basis` 中引用 memory 记录 / contribution 记录 / ai 观察。可注明："分数规则可由 circle 自定义（如声誉×贡献加权），契约只要求证据可追溯，不强制算法。"

### 4.2 circle 需要自己的契约

`circle_id` 出现在信封、memory、consensus、contribution 四处，但"圈子"本身（如何创建、谁能加入、圈间如何关联、解散后记忆归属谁）没有契约。对一个社区操作系统，**圈子是最基本的容器**，隐式存在会很快失控。

建议：新增 `contracts/circle.v1.json`（最少字段：id、name、parent、members、status、created_by、created_at），并在 registry 中把 circle 列入 `required_in_default_mode`（或明确"隐式一等端口"）。

### 4.3 证据链的"optional"漏洞

`identity.v1.json` 的 `capability_trace.source_port` 枚举 `["contribution","memory","consensus","optional"]`——`optional` 意味着任何人都能声称"我有能力"，与"人不能自封能力"（append_trace 仅 system）的原则相冲突：写入是 system 管的，但来源标成 optional 就绕过了证据语义。

建议：`optional` 拆为显式端口列表（如 `job_match`、`mbti`、`ai_observed`），并标注 `weight: evidence | auxiliary`；白名单之外一律拒绝。

### 4.4 八角梯：加一句话逻辑

当前顺序：observer → participant → experimenter → proposer → steward → organizer → actor → petitioner。两个易混点：
- **proposer（提议，4 级）vs petitioner（提案，8 级）**：中英文都几乎同名，但一个在中间一个在顶端——语义负担过重。
- **steward（主理）→ organizer（组织）→ actor（行动）**：为什么"主理"低于"组织"？为什么"行动"在最顶端？如果无因果链说明，新成员看不懂，设计小组也无从表达。

建议：`roles.v1.json` 增加 `ladder_logic`，每级一句"新增的责任"，例如：
- proposer：能把想法变成可评议的提议
- steward：能主持一件事的运转（主理）
- organizer：能组织多方协作（组织）
- actor：能牵头把共识变成行动（行动）
- petitioner：能提出改变共同体规则的提案（提案）

若语义确认不了，考虑调整命名（如 8 级改"建议者 → 提案人"错开），或至少在 L0 文档给一句话因果链。

## 五、P2 详解

### 5.1 "格契"缺电梯陈述

仓库没有任何地方解释"gfcc 是什么缩写、为什么叫格契"。建议 README 顶部加：

> **格契（GFCC）**——社区共同体的"牵引力"层：把"记得住、协商得了、贡献兑得现"做成可交付的体系。方向盘在共同体手里（Tractor：你掌方向，我出力气）。

### 5.2 契约版本演进策略

契约是权威，就必须回答"权威怎么变"。建议补 `docs/VERSIONING.md`：semver 规则（breaking change 必须升主版本）、弃用期（如 intent 别名的处理）、CHANGELOG、以及"任何契约变更须先过 L-1 价值层评审"。

### 5.3 gfcc 与 Tatha 澄清

README 把 Tatha 画成中央大脑（实现），ports 提纲把 Tatha 列为方法学来源。建议在权威层级表补一行：**gfcc = 契约层（真源）；Tatha = 实现层（`POST /v1/ask` 的一个具体实现，可替换）**。避免读者混淆"谁是权威、谁是执行"。

### 5.4 部分成功 / 事务语义

多端口组合下"半成功"是常态（memory 写了、consensus 挂了）。`AskResponse.status` 只有 ok/pending/denied/error/unknown，无 partial。建议：
- `status` 增加 `partial`；或
- `result` 内按端口给独立状态回执，并注明"已成功的子操作不可回滚，未成功的可重试"。

### 5.5（补充）与对外叙事的对齐

gener社区.pptx 演示了 CON/GOV/DAO/SBT/治理权不可买；格契 `contribution.v1.json` 明确"不上链、积分不是主叙事"。两者不矛盾（链上是远期可选），但需要一句对外口径，避免工程契约与品牌演示打架：

> "v1 的格契不依赖链；链是未来可选的一层，不是现在的承诺。"

## 七、术语对照与红线（沿用项目定稿）

| 项目定稿 | 格契现状 | 建议口径 |
|---------|---------|---------|
| 8 角色（旁观/参与/尝试/提议/主理/组织/行动/提案） | 八角梯 ✓ | 一致，补 ladder_logic |
| 4 类营造师 | 无 | identity 补 builder_tag |
| AI 洞察层（RAG × 观察评估） | 只有 llm/provider | memory.observe + ai_observed |
| 双轨对话（协作 × 教练） | 无 | 信封补 dialog_mode（P1 追加项） |
| 7 库超级底座 | Dual 七库（缺"价值"） | 恢复方法论价值 |
| CoCo 贡献治理 | contribution ✓ | 一致，补 appeal 后可回写 trace |
| 信任接缝 | ethos | 一致 |

**红线**：不引入 PK 式对抗表达；不把 AI 写成替代人的决策者；治理权不可买卖；"有结果 ≠ 成功"（双向确认）贯穿全契约。
