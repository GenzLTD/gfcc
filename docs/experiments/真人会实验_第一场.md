# 真人会实验 · 第一场 v2（信封场：建圈 → 复盘）

> 修订说明（v1 → v2）：对照 `dispatcher.py` / `ports/*` 现状后，v1 有 4 处断点
> （B0 身份来源、B1 入座语义、B2 共识断链、B3 兑现断链），本版按方案 A 修订——
> 全程走 `POST /v1/ask` 信封 + 具名令牌，验证三判据数据链；**不开公网页面**，
> D1–D5 按钮本场不启用（页面冒烟另开一场，见方案 C）。
>
> 目的（不变）：用一场最小真人会验证围坐三判据 ——
> 1. **记得住**：散会后隔日召回当时的圈与结论（证据链引用）；
> 2. **有共识**：结论有合意引擎 `consensus_score + parties + 全员本人 ack` 支撑；
> 3. **兑得现**：会上承诺的贡献有 `capability_trace` 可回溯。

## 前置条件（B0 修订）

- gfcc_kernel 已在跑（`/health` 返回 `status=ok`）。
- **3 把具名令牌**：`tester-a`（主持人）/ `tester-b` / `tester-c`。
  - 身份来源 = 令牌 `sub`（`KernelPolicy.sub`），**不靠 session_id**；换 token 换人。
  - 无真实令牌时，stub 模式（无 `ETHOS_AUTH_SECRET`）下可带 `Authorization: Bearer <sub>` 联调。
- LLM 可用（`/health` 的 `llm` 为 ollama 或等效）——仅影响端口分类，不参与讨论总结。
- 环境前提：`GFCC_MODE` 默认 `gfcc.default`（全仓未配置即默认），
  **L3 加分项默认不激活**；如需激活，启动前设 `GFCC_MODE=profile.demo` 且
  agentmemory gateway（3210）/ demopeter（5220）可达。

## 实验步骤

全程 `POST http://127.0.0.1:5211/v1/ask`，请求体结构：

```json
{
  "message": "<自然语言指令>",
  "context": {"port_hint": "<端口>", "circle_id": "<同圈>", "session_id": "<会话>"}
}
```

| # | 步骤 | 执行者 | message（示意） | port_hint | 端口证据 | 验收标准 |
|---|---|---|---|---|---|---|
| 1 | 建圈 | tester-a | `创建围坐圈 第一场` | `circle` | 响应 `data.circle_id` | 圈落库；建圈者即 organizer 入座 |
| 2 | 入座（B1） | tester-a/b/c | `加入围坐圈` | `circle` + 同 `circle_id` | `circle_members` 落库（3 人） | 3 人都在 members（sub + role + joined_at） |
| 2b | 画像展示（optional） | 任一 | `展示我的画像` | `identity` | profile 只读展示 | 可展示；**无写入**（identity 不入座） |
| 3 | 议题入库 | tester-a | `记住议题：<议题文字>` | `memory` | 响应 `data.record.id` | 落 sqlite；抄下 record id 备用 |
| 4a | 提议（B2） | tester-a | `提议：<结论文字>` | `consensus` + 同 `circle_id` | proposal id；`parties` = 3 个真人 sub | 状态 `proposed`；parties 不再硬编码假人 |
| 4b | 打分（B2） | tester-a | `打分 <proposal_id> 90 <理由>` | `consensus` | `score_evidence`（by_sub=主持人）+ 状态 `awaiting_ack` | score ≥ 阈值（85）→ `awaiting_ack` |
| 4c | 确认（B2） | tester-a/b/c 各一次 | `确认 <proposal_id>` | `consensus` | `acks` 3 人 | 全员本人 ack → `consensus_verified` |
| 5 | 贡献认定（B3） | 交叉：tester-b 认 tester-a 等 | `认定 tester-X 完成了 <承诺事项>` | `contribution` + 同 `circle_id` | record 状态 `attested`（attestor=本人、subject=他人） | 不能自我认定（本人=subject 会拒绝） |
| 5b | 兑现（B3） | tester-a | `兑现 <record_id>` | `contribution` | `fulfilled:true` + `minted_trace_id` | identity `capability_trace` 增长（判据3） |
| 6 | 散会抄 id | tester-a | `记住结论：<结论文字>` | `memory` | 新 record id | 结论可回溯（判据2 证据链起点） |
| 7 | 复盘 | 隔日 tester-a | `回忆上次围坐的结论` | `memory` | 返回引用步骤 6 的 record id | **判据1 记得住** |

## 三判据判定口径（对齐契约）

- **判据2 有共识**：契约口径 = `score ≥ threshold` **且** `parties` 全部本人 `ack`
  → 状态 `consensus_verified`。仅 score 高不够，AI 不能代替真人 ack。
- **判据3 兑得现**：`contribution.fulfill` → `minted_trace_id` 写入
  identity `capability_trace`（`source_port=contribution, weight=evidence`）。
  **已知限制**：contribution/identity 为内存 stub，重启即丢——本场接受
  「当场上 evidence 存在」为证据，重启丢失记入失败记录，作为持久化优先级输入。
- **判据1 记得住**：步骤 7 的召回必须引用步骤 6 的 record id（`keyword 弱匹配`，
  隔日同场可复现；语义召回见 L3 加分项）。

## L3 加分项（`GFCC_MODE=profile.demo` 且服务可达时）

- 步骤 3 前先 `POST /v1/knowledge/query {"question":"..."}` 查知识库，
  把 demopeter 输出作为协商参考证据，随议题一并存入 memory record；
- agentmemory_iii（gateway 3210）接管 store 槽后，步骤 7 的 recall 走语义召回，
  且 memory 证据可跨重启保留（对比本场 sqlite 键字匹配）。

## 判定规则

- **过**：步骤 7 真的引用了步骤 6 的 id（记得住）；步骤 5b 的 `minted_trace_id`
  真实落入 `capability_trace`（兑得现）；步骤 4c 状态 `consensus_verified` 且
  acks 覆盖全部 parties（有共识）。
- **不过**：任何一步靠口头「我以为」带过、没有端口证据 —— 直接记入「失败记录」，
  注明是哪一判据/哪一步断了，作为下一场实验的输入。
