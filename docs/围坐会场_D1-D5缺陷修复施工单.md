## 0. 共享改动点（D2 / D3 / D5 公共底座，先落这一步）

三条缺陷共用「状态机加态 + 终态集合统一 + 落库加列 + 契约次版本 + 安全映射」，一次改完，避免三次动同一批文件。

### 0.1 状态机（`ports/consensus.py`）

`VALID_STATUSES` 现有：`proposed / scored / below_threshold / consensus_passed / awaiting_ack / consensus_verified / expired / failed`（`expired` 已有，缺触发）。

- 新增 **`rejected`**：任一人持异议（带理由）→ 提案作废，释放 pending 阻塞。
- 新增 **`withdrawn`**：proposer 自己撤回（未达终态）→ 提案作废，释放 pending 阻塞。
- **终态集合（钉死，全文唯一口径）**：

```python
TERMINAL = {"consensus_verified", "rejected", "withdrawn", "expired", "failed"}
```

  所有「这提案还占不占位」的判断一律按 `status in TERMINAL` 走，**禁止**再写 `status != "consensus_verified"`（见 §0.5）。
- 端口新增两个操作（签名对齐现有 `PortOpResult`）：
  - `reject(proposal_id, sub, reason)`：仅 `sub ∈ parties`；**仅允许** `status ∈ {"awaiting_ack", "consensus_passed"}`（`proposed` / `below_threshold` 不在本单会场路径——`propose+score` 原子提交不落 proposed；低分落 below_threshold 时走撤回，不需要异议；终态一律拒绝）；`reason` 必填（空白 → `ok=False, error="reason is required"`）；成功 → `status="rejected"` 并记录 `rejected_by / reject_reason / rejected_at`。
  - `withdraw(proposal_id, sub)`：仅 `proposal.created_by == sub`；**仅允许** `status ∈ {"awaiting_ack", "consensus_passed"}`（`consensus_verified` 不可撤回）；成功 → `status="withdrawn"` 并记录 `withdrawn_by / withdrawn_at`。
- 两者**都不动地板**：proposer 仍持发言权，可改提新句；有不同观点的人在下一轮自己拿地板时再提。
- 加态是 additive：`score()` / `acknowledge()` / `expire()` 里的状态闸语义不变，新状态天然被这些闸拒收（不可再被 ack / 再被 score / 再被 reject / 再被 withdraw）。

### 0.2 落库（`circle_flow.py`）

`proposals` 表加 5 列（**新库走 `_SCHEMA` 的 `CREATE TABLE`，存量库走幂等迁移**）：

```sql
ALTER TABLE proposals ADD COLUMN rejected_by  TEXT;
ALTER TABLE proposals ADD COLUMN reject_reason TEXT;
ALTER TABLE proposals ADD COLUMN rejected_at   TEXT;
ALTER TABLE proposals ADD COLUMN withdrawn_by  TEXT;
ALTER TABLE proposals ADD COLUMN withdrawn_at  TEXT;
```

- **迁移纪律（踩坑先例）**：SQLite 无 `ADD COLUMN IF NOT EXISTS`，且 G6 时期 `CREATE INDEX` 写进 `_SCHEMA` 对存量库 `executescript` 直接报错。做法：`_SCHEMA` 里 `CREATE TABLE IF NOT EXISTS proposals (...)` 直接带新列（全新库一次到位）；另加幂等迁移块，用 `PRAGMA table_info(proposals)` 检查缺列才 `ALTER TABLE`（`__init__` 里 `conn.executescript(_SCHEMA)` 之后跑）。
- 写库复用现有 `update_proposal(proposal_id, **fields)` 通用字段更新（新列是普通 TEXT，不进 `_JSON_COLUMNS`，无需改）。
- `_hydrate()` 恢复时新键会进入内存 dict 并暴露给 API——**有意为之**（状态卡要显示"被谁反对、什么理由"），属 additive 字段变更，契约同步补 properties（见 §0.3）。
- D3 超时的 TTL 常量：`CIRCLE_PROPOSAL_TTL_SECONDS` 环境变量，默认 `86400`（24h，对齐原缺陷建议）；`0` = 禁用。**边界写死**：TTL 解的是**隔夜僵尸场**（人走圈凉、卡一条 awaiting_ack 到明天）；解不了**当场漏点**（D1 那 10 分钟——当场靠 D2 异议 / D3 撤回）。**不许有人指望超时救当场**。

### 0.5 pending 闸统一（评审硬缺口，必须先于 D2/D3/D5 落）

**现状的洞**：`circle_web.py:240-242` 的 `api_propose` 与 `circle.html:403` 的 `pendingCount` 都写 `status != "consensus_verified"`；状态卡 tag（`circle.html:448-450`）非 verified 一律「等待确认」。只加 rejected/withdrawn/expired 不换过滤器 → 驳回/撤回/超时的提案**永远占着 pending**，新提案照样 400、拍板卡照样藏、tag 永远显示「等待确认」。

**钉死改法（三处同口径，全部改用 §0.1 的 `TERMINAL`）**：

1. 后端 `circle_web.py` `api_propose`：`pending = [p for p in _proposals_in(...) if p["status"] not in TERMINAL]`（`TERMINAL` 由 `ports/consensus.py` 导出，web 层 import 同一常量，不各自抄一份）。
2. 前端 `circle.html` `pendingCount`：`p.status` 命中终态集合才算释放（`["consensus_verified","rejected","withdrawn","expired","failed"].indexOf(p.status) >= 0`）；banner 文案「还有 N 条在等待确认」与拍板卡显隐逻辑沿用同一集合。
3. 状态卡 tag：`verified → 已达成`；`rejected → 已驳回`；`withdrawn → 已撤回`；`expired → 已作废`；其余 → 等待确认。

**惰性超时挂两处（评审修正）**：只挂 `get_status()` / `api_status` 不够——`api_propose` 走 `_proposals_in()`（`consensus.list_all()`），不经过 `get_status()`，没人开页面时超 TTL 的 `awaiting_ack` 仍会挡住下一条。抽 `_expire_stale(circle_id)`：

- 位置：`ports/consensus.py` 提供 `expire_stale(ttl_seconds)`（遍历该圈 `awaiting_ack` 且 `created_at + TTL < now` 的提案 → `expire()` 落库）；`circle_web.py` 包 `_expire_stale(circle_id)` 一次调用。
- **挂载点（两处都挂）**：`api_status`（读路径，顺手清）与 `api_propose`（写路径——propose 前先清，保证旧僵尸不挡新句）。
- 惰性判定**不做定时器**、不引常驻线程。

## 2. D2 — 无异议/反对通道（表达同意/阐述不同观点）

**现状**：ack 只有确认，无任何"不同意/异议"入口；不同观点只能"不点确认"挂死全场，或干等下一轮自己拿地板。系统里没有"反对"的记录语义。
**目标行为**：入座成员（party）对未达成的拍板句可提交**异议（必带理由）**→ 提案置 `rejected` → pending 阻塞释放（§0.5 换掉过滤器后立即可提新句）→ proposer 可改提新句；`rejected` 提案留在状态卡（含理由），作历史证据。此即用户测试中缺失的"表达同意或阐述不同观点"栏目。

### 改动点

- 共享：§0.1 `reject` 端口操作（允许态 `awaiting_ack / consensus_passed`）+ §0.2 落库 3 列（rejected_*）+ §0.3 契约次版本 1.2.0 + §0.5 pending 闸统一。
- web（`circle_web.py`）新增路由：

```
POST /circle/api/reject   body {circle_id, proposal_id, reason}
```

  - 鉴权 `_sub(request)`；`circle.status == "dissolved"` → **400 `"circle dissolved"`**（与 §5 统一，防 API 打到已解散圈）；proposal 属于该圈（对齐 `api_ack` 的 400）；`reason` 空白 → 400 `"reason is required"`；端口拒绝（非 party / 允许态外）→ 400 透传；未知 proposal → 404。
  - 响应：`{circle_id, proposal_id, proposal}`。
- 前端（`circle.html`）：
  - 状态卡每个未达成提案，`iAmParty && !myAcked` 时渲染两个按钮：「我本人点确认」（现有）+「有异议 · 阐述观点」（新，点击展开必填理由输入框 + 提交）。
  - `rejected` 提案渲染 `status-tag`「已驳回」+ 理由行「异议（{sub}）：{reason}」（§0.5 第 3 点）。
- 可选挂分歧度（不阻塞本单）：`consensus_math.disagreement_mass` 已存在（`consensus_math.py:110`），后续做 evidence 强度时把 reject 理由按 dm 计分——本单**不做**，仅备注。

## 3. D3 — 无撤回、无超时作废

**现状**：proposer 不能撤回自己的 pending 提案（提错/改主意只能等别人 ack 或 leave/解散兜底）；无超时，卡死的场无自动清理。端口已有 `expire()`（`consensus.py:152`）但**无任何触发**。
**目标行为**：proposer 可撤回未达终态的本提案（`withdrawn`，释放 pending）；`awaiting_ack` 超 TTL 惰性作废（`expired`，§0.2 边界：只管隔夜僵尸场，当场靠 D2/D3）。

- web（`circle_web.py`）新增路由：

```
POST /circle/api/withdraw   body {circle_id, proposal_id}
```

  - `circle.status == "dissolved"` → 400 `"circle dissolved"`；仅 proposer（端口闸）；允许态外/终态 → 400；未知 proposal → 404。
  - 响应：`{circle_id, proposal_id, proposal}`。
- 前端（`circle.html`）：`proposer` 视角对未达成提案渲染「撤回本条」（二次确认），成功后提示可改提新句；`withdrawn`/`expired` 提案按 §0.5 tag 显示「已撤回」/「已作废」。

## 4. D4 — token 粘贴断行 → 401 无提示

**现状**：08-28 三把 token 粘贴断行损坏。根因有两层：`circle.html:222` `enter()` 只做 `.trim()`，**清不掉行内换行/空白**；鉴权失败统一裸 `401`，前端文案只有"入场失败：…"（`circle.html:237`），真人看不出是令牌坏了。
**目标行为（评审修订，收窄）**：**前端为主**——粘贴时剥掉全部空白（断行令牌直接能进）；入场失败按状态码给可操作文案。**不做**全局鉴权格式预检（`app._verify_request` 被 `/v1/ask` 与 `/circle/api/*` 共享，改 401→400 既踩"不改既有状态码语义"纪律、又波及其他端点；§10.1 原写 400 是可选，不升为必做）。

### 改动点

- 前端（`static/circle.html`）：
  - `enter()`：`var t = $("token").value.replace(/\s+/g, "");`（剥掉全部空白，解决微信断行；`trim()` 保留为无空白时判空）。
  - 入场失败 `.catch`：按 `e.status` 分支文案——`401` → 「令牌无效或已过期，检查是否完整（不要带换行/空格，应有开头 eyJ 与结尾点号），可向主持人再要一条」；其他 → 原「入场失败：{message}」。
  - **不动** `redeemInvite`（走邀请码 `?i=` 兑换，不是 JWT 粘贴场景；其现有失败文案已含「请向主持人再要一条链接，或粘贴备用令牌」，保留）。
- 后端：**默认不做**。可选增强（单独批注，不并入本批）：若后续仍想区分"格式坏"与"验签失败"，只许在 `circle_web._sub` 内加格式预检（非 `Bearer ` 前缀 / 非三段式 / base64 解码失败 → `400`），**不动 `app._verify_request`**——届时须连带改 `test_unauthorized_strict_mode`（现用 `bad.token.here`，其 payload 段非合法 base64，会被预检判 400；改用一个三段式 base64 合法、签名假且验签失败的 token，断言**仍 401**）。

## 5. D5 — 解散无入口

**现状**：端口 `circle.dissolve` 已实现（`ports/circle.py:238`，仅 `created_by`，`status → dissolved` + `dissolved_at`，落库 `update_circle_status` 不删行），`join` 对非 active 圈已回 `400 circle not joinable`——**只差接线**：`/circle/api` 无 dissolve 路由、页面无按钮。真人散会只能全员 leave，圈永远 `active` 挂着。
**目标行为**：建圈者（`created_by`）可一键解散本场（二次确认）；解散后状态卡显示「已解散」，join / propose / ack / reject / withdraw 一律 400，历史不删。

### 改动点

- web（`circle_web.py`）新增路由：

```
POST /circle/api/dissolve   body {circle_id}
```

  - 鉴权后仅 `created_by`，**其余成员 → 403**（对齐围坐权限先例：`api_propose` 非地板即 403；**不是** 400 透传——权限失败与请求错误分开）；未知圈 404。
  - 响应：`{circle_id, status: "dissolved"}`。
- **解散后闸（评审补充，钉死）**：`api_propose` / `api_ack` / `api_reject` / `api_withdraw` 对 `circle.status == "dissolved"` 一律 **400 `"circle dissolved"`**（前端会藏按钮，但 API 仍可打到已解散圈；join 已 400 `not joinable`，不改）。`leave` / `observe` / `unobserve` 保持放行（退出语义无害）。
- 前端（`circle.html`）：
  - 状态卡顶部，仅建圈者视角渲染「解散本场」按钮（二次确认，文案"解散后历史保留、不能再入座，确定？"）。
  - 状态卡对 `circle.status == "dissolved"` 渲染「已解散」标识，隐藏确认/异议/撤回/解散按钮。
  - `api_status` 已返回整个 circle（含 status/dissolved_at），无需改后端响应形状。
